# 1주차 핵심 개념과 내 실행 결과

## 데이터 엔지니어링과 MLOps

- 데이터 엔지니어링: 데이터를 수집하고 저장·변환하여 믿을 수 있는 입력을 계속 공급한다.
- MLOps: 그 데이터로 만든 모델의 실험·배포·감시·재학습을 관리한다.
- 공통 연결점은 피처다. 학습과 서비스에서 같은 뜻의 피처를 같은 규칙으로 계산해야 한다.

## 이번 실습 흐름

제공된 실제 API 응답 JSON → 성공 코드와 목록 구조 검사 → 측정값 숫자 변환 → 결측 분류 → 건수·평균 계산 → 제출 JSON 저장.

이번 실행은 저장된 응답 재계산이다. 실시간 API 호출 단계는 수행하지 않았다.

## 응답을 읽는 순서

1. `response.header.resultCode`: API 자체의 처리 결과. 이번 스냅샷은 `00`.
2. `response.body.totalCount`: 전체 레코드 수. 이번 스냅샷은 40.
3. `response.body.items`: 측정소별 레코드 배열.
4. `pm10Value`, `pm25Value`: 문자열 값을 숫자로 바꿔 계산하며 `-`, 빈 문자열, null은 0이 아닌 결측으로 처리.

## 결과를 설명하는 문장

- PM10 보고 40개와 결측 0개를 더하면 측정소 레코드 40개다.
- 평균은 보고된 값으로만 계산했다. PM10 평균은 20.0, PM2.5 평균은 12.7 μg/m³다.
- 관측 시각은 2026-06-28 22:00이다. 재실행한 날짜의 최신 대기질이라는 뜻은 아니다.
- 이번에 결측이 없었다는 사실만으로 모든 시각에 결측이 없다고 결론 내릴 수 없다.

## 제출 전 스스로 설명해 볼 질문

- 문자열 `"21"`에 바로 산술 계산을 하면 왜 문제가 될까?
- 결측을 0으로 바꾸면 평균이 어떻게 달라질까?
- HTTP 요청이 성공했어도 API 응답의 성공 코드를 확인해야 하는 이유는?
- `pm10_reported + pm10_missing = station_count`가 깨지면 어떤 집계 오류를 의심할까?

이 파일은 학습 보조용이며 필수 제출물로 확인된 문서는 아니다.
